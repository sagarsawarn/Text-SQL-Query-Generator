1. Project overview

Text2SQL-AI is a Streamlit web application that lets a user describe a data question in ordinary language and receive a SQL SELECT query. The full application can either use a manually described schema or load one or more CSV/XLSX files into a temporary in-memory SQLite database. An OpenAI or Google Gemini chat model uses the schema, sample rows, distinct values, and the question to generate SQL.

The main implementation is in main.py. It provides registration/login, a dashboard, model settings, two data-input modes, query history, result previews, CSV downloads, and a small automatic chart. The reusable text-to-SQL engine is in process/rag_process.py.

Important: the current production-style flow is streamlit run main.py. app.py is a smaller legacy/demo entry point and does not provide the full authentication and upload workflow.

2. Capabilities and limitations

Natural-language SQLGenerate SQL from a question using an LLM and schema context.
Two data modesDescribe a schema as text, or upload CSV/XLSX files.
Two providersChoose an OpenAI-compatible GPT model or a Google Gemini model.
Safe previewOnly a single read-only SELECT is previewed from uploaded data.
Self-correctionFailed queries and empty-result filters may be sent back to the model for one correction attempt.
Usable resultsDisplay a dataframe, download CSV, and show a basic chart when the result is suitable.

Current boundaries

  • Uploaded data is loaded into an in-memory SQLite database; it is not a permanent database connection.
  • The text-schema mode generates SQL but does not execute it because it has no database engine behind the free-form description.
  • The application does not currently connect to MySQL, PostgreSQL, or SQL Server despite older documentation mentioning those systems.
  • API keys are required for non-demo AI generation and are never saved to users.json.
  • Generated SQL is model output. Users should review it before relying on business-critical results.

Request lifecycle

  1. main.py initializes Streamlit configuration, authentication state, and general session defaults.
  2. An unauthenticated visitor sees the login/register page. An authenticated user sees the workspace and model sidebar.
  3. The sidebar chooses provider, model name, and API key. The key can come from the sidebar or .env.
  4. The user supplies schema text or uploads files, then enters or records a question.
  5. Text2SQL builds a schema description. For files, Pandas loads each file and SQLAlchemy writes it to SQLite memory.
  6. The prompt in process/prompt_process.py asks the model for SQL only and tells it to use only known table/column names.
  7. The response is cleaned of Markdown fences. For file mode, a single read-only SELECT is validated and executed.
  8. Errors can trigger a model-assisted correction. Empty results can trigger one filter-value correction.
  9. The UI shows SQL, an explanation, a result table, a CSV download, and a chart when applicable.

5. Installation and configuration

Prerequisites

  • Windows, macOS, or Linux.
  • Python 3.10+ recommended.
  • Internet access for OpenAI/Gemini calls.
  • An OpenAI API key or Google AI/Gemini API key for non-demo requests.

Install

cd Gen-AI-Powered-Text-to-SQL-Query-Generator
python -m venv .venv
# Windows PowerShell:
.\.venv\Scripts\Activate.ps1
# Windows Command Prompt:
.\.venv\Scripts\activate.bat
python -m pip install --upgrade pip
pip install -r requirements.txt

Configure the API key

copy .env.example .env
# Edit .env:
OPENAI_API_KEY=your_openai_key
GOOGLE_API_KEY=your_google_key

For GPT, OPENAI_API_KEY is checked. For Gemini, GOOGLE_API_KEY and then GEMINI_API_KEY are checked. The sidebar key field overrides the environment key for the current session.

Do not commit secrets. Keep .env local, restrict access to the project folder, and rotate a key immediately if it is exposed.

6. Starting the application

Recommended full application

cd Gen-AI-Powered-Text-to-SQL-Query-Generator
.\.venv\Scripts\Activate.ps1
streamlit run main.py

Streamlit prints a local URL, normally http://localhost:8501. Open it in a browser. Stop the server with Ctrl+C.

Legacy application

streamlit run app.py

Use this only when intentionally testing the older simple flow. It asks for a question and calls the placeholder in sql_generator.py; it is not the recommended application entry point.

7. End-user workflow

  1. Open the Streamlit URL.
  2. Choose Register, enter name/email/password, and submit. Passwords must be at least six characters and are stored as PBKDF2-SHA256 hashes with a random salt.
  3. Return to Login and sign in.
  4. In the sidebar, open Model Settings, choose GPT or Gemini, choose a model, and confirm the API key is configured.
  5. Choose Text2SQL in the workspace navigation.
  6. Choose Text Input or Upload File.
  7. Provide the data context, enter a question, and click Generate SQL.
  8. Review the generated SQL and explanation. If files were uploaded, review the result preview.
  9. Download results as query_results.csv if needed.
  10. Use Query History to search, reuse, or clear previous generated queries. Use Logout when finished.

8. Text Input workflow

Text Input is useful when the schema is known but the application does not have a file to load. Enter a clear table description, for example:

employees table with columns:
id, name, department, salary, age

Sample rows:
1, Rahul, IT, 55000, 24
2, Priya, HR, 45000, 28

Then ask: “Show employees from the IT department earning more than 50000.” The model receives the schema text and question and returns SQL. Because no executable database is created for free-form text, the UI displays the SQL but does not preview rows.

Tips for accurate text schemas

  • Use exact table and column names.
  • Include data types or representative sample rows when filters depend on values.
  • Explain relationships explicitly if multiple tables are described.
  • Ask one focused question at a time.
Try Demo: the built-in employee examples run locally and do not require a model or API key. They are useful for checking the interface.

9. CSV/XLSX upload workflow

  1. Choose Upload File and upload one or more .csv or .xlsx files.
  2. The first uploaded file becomes the primary table named data. Additional files use the filename without extension as the table name.
  3. CSV files are read with pandas.read_csv; Excel files use pandas.read_excel.
  4. Each dataframe is written to the same in-memory SQLite engine with if_exists="replace".
  5. The application inspects table names, columns, sample rows, row counts, distinct text values (up to 25), and numeric ranges.
  6. The enriched table information is sent to the model with the natural-language question.
  7. The returned query is validated and previewed against the in-memory data.

File naming and data tips

  • Use simple filenames such as orders.xlsx; filenames become table names for files after the first.
  • Use unique, SQL-friendly column names without blank headers.
  • Keep the first row as the header row.
  • Remove sensitive data before uploading unless the deployment is approved for that data.
  • Large files increase memory usage and schema-inspection time.

10. SQL generation and safety controls

Prompt behavior

The generation prompt instructs the model to output SQL only, use only known tables/columns, prefer a simple SELECT, compare text case-insensitively, and return exactly I don't know when the question is unrelated or cannot be answered from the schema.

Read-only validation

is_read_only_select removes comments and checks that the query begins with SELECT and contains no additional semicolon. This blocks common write operations and multiple statements during preview. The query then runs through Pandas against the temporary SQLite connection.

Scope of protection: this is an application-level preview guard, not a complete SQL security boundary. Do not expose the app to untrusted users or sensitive databases without stronger isolation, authorization, auditing, and database permissions.

Automatic correction

  1. If execution fails, the original question, schema, failed SQL, and database error are sent to the correction prompt.
  2. The model returns a corrected SQL query.
  3. The corrected query is run again through the same read-only validation.
  4. If a valid query returns zero rows, the application makes one correction attempt focused on distinct values and case-insensitive filters.

11. Results, charts, and exports

  • Generated SQL: shown in a SQL code block.
  • SQL Explanation: generated locally by a regex-based explainer by default. The optional AI explanation path is disabled by USE_AI_EXPLANATION = False.
  • Query Results: displayed as a Pandas dataframe for uploaded data.
  • CSV download: downloads the result as query_results.csv.
  • Chart: when the result has at least one numeric and one text column and no more than 30 rows, a bar chart is rendered. ID-like columns are avoided when another numeric column exists.
  • Query history: non-demo generated queries are stored per user. Entries are marked as having results when a non-empty result is returned.

12. Authentication and stored data

Registration and login

Users are stored in JSON. Email addresses are normalized to lowercase. Passwords are never stored in plain text: a random 16-byte hexadecimal salt and PBKDF2-HMAC-SHA256 hash are stored. Login uses constant-time comparison through hmac.compare_digest.

Where data is stored

DataLocation / lifetime
API key typed in sidebarStreamlit session state only; not written to disk by the project.
Provider/model preferenceSaved per user in users.json; the API key is not saved.
Query historySaved per user in users.json.
Uploaded dataLoaded into a temporary in-memory SQLite engine for the current request/session flow.
Session stateManaged by Streamlit and reset when the session ends or is refreshed according to Streamlit behavior.
Deployment note: users.json is a local JSON store, not a multi-user production identity system. Use a proper identity provider and database-backed persistence for production.

13. Operations and maintenance

Routine startup checklist

  1. Activate the intended virtual environment.
  2. Verify .env exists and contains the correct provider key.
  3. Run pip install -r requirements.txt after dependency changes.
  4. Start streamlit run main.py.
  5. Use the built-in demo to validate the UI before testing a real key or file.

Dependency updates

Update requirements.txt deliberately, reinstall in a clean environment, and verify both GPT and Gemini paths. Pay particular attention to Streamlit, LangChain, SQLAlchemy, Pandas, OpenAI, and Google client compatibility.

Log and error handling

The application uses Python logging for detailed exceptions while presenting a shorter user-facing message. When diagnosing an issue, capture the exception type, provider/model, input mode, file type, and whether the demo path works. Never include API keys in logs or support tickets.

15. Security and production checklist

  • Use HTTPS and a reverse proxy for any non-local deployment.
  • Never commit .env, API keys, real user records, or sensitive uploaded data.
  • Replace JSON authentication with an identity provider and a database-backed user store.
  • Use per-user authorization and rate limits for model calls and file uploads.
  • Set upload size/type limits and scan files according to organizational policy.
  • Use a database account with read-only permissions if connecting to an external database.
  • Keep LLM prompts and uploaded data within the approved data-processing boundary.
  • Review generated SQL before using it for decisions or exporting sensitive data.
  • Add structured audit logs that exclude secrets and unnecessary personal data.
  • Pin and periodically update dependencies, and run security scanning in CI.

16. Developer extension guide

Add a new provider

  1. Add its environment key name in utils.py.
  2. Add provider/model options in components/sidebar.py.
  3. Construct the provider client in Text2SQL.__init__ in process/rag_process.py.
  4. Add the dependency to requirements.txt.
  5. Test generation, correction, timeout, and quota failures.

Change prompts

Edit process/prompt_process.py. Preserve the SQL-only contract, schema-only constraint, and explicit fallback response. Test both a straightforward query and an unrelated question.

Change the schema pipeline

Edit build_table_info and Text2SQL.init_db. Keep table names, columns, sample values, and row counts consistent with the actual SQLite engine. If adding another file type, update the uploader type list, parser, and documentation together.

Change result behavior

Keep validation in run_query and route new execution paths through it. Do not bypass the single read-only SELECT guard for convenience.
